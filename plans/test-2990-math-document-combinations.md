# Plan: 数式デリミタ判定を、記事の実物に近い組み合わせで固める (#2990)

Issue: https://github.com/receptron/mulmoclaude/issues/2990

## 1. なぜ必要か

`packages/markdown-utils` の直近5コミットは、すべてインライン `$…$` の
ルール5（本文が数式か金額か）を狭めた記録である。4回とも「ルール単体では
正しいが、実際の文書では別の読み方がある」形で見つかっている。

既存の `test_mathExtension.ts` はルールを1つずつ検証しており、
**ルール同士・markdown 構造との組み合わせ**を見ていない。想定読者は
ブログ記事（金融・数学・IT）なので、抜けはそこに出る。

## 2. 方針

`test_mathExtension.ts` は「ルールの単体テスト」として残し、新しい
`test_mathInDocuments.ts` を「記事としての組み合わせテスト」に充てる。
2つのファイルの役割を分けることで、次にルールが狭まったとき、
どちらを直すべきかが名前から分かる。

判定は `typeset(src)` が返す `["i:<tex>", "D:<tex>"]` の**配列比較**で行う。
「どの数式が組まれたか」と「余計なものを飲み込んでいないか」を1つの
アサーションで見られるため、組み合わせのケースが読める。

## 3. 内容

| セクション | 見るもの |
|---|---|
| 数の形 | 28通り（金額13・数式11・壊れた形4）。英/独/仏/西のロケール、曖昧な形。各行に「なぜそう読むか」 |
| 金融記事 | 一文に価格2つ、価格表、`US$5`、`$5-$10`、`\$5`、価格と数式の混在 |
| IT記事 | `$PATH` / `$HOME` / 位置引数 / `$(date)`、コード4形式 |
| markdown 構造 | 強調・見出し・引用・ネストリスト・表・リンク・脚注・HTML隣接（17通り） |
| display | `$$…$$` のブロック／インライン、リスト・引用の中、通貨判定を受けないこと |
| TeX 受け渡し | HTML 特殊文字のエスケープ、入れ子波括弧、`\href` は下流に渡すこと |
| 改行・空白 | CRLF、全角スペース、タブ |
| 単体境界 | 拡張経由では届かない `isPlausibleInlineMath` の契約 |

グラフ（mermaid）と同じ Marked インスタンスに載せたときに互いを
壊さないことも1件見る。

## 4. 検証

**ミューテーションで検出力を実測する。** ルールを1つずつ壊し、対応する
テストが赤くなることを確認する。「テストが通った」ことは、テストが
何かを守っている証拠にならない。

散文側は「数式にならなかった」だけでは足りない。トークナイザが本文ごと
飲み込んで何も出力しない回帰は、価格が数式になるのと同じくらい悪いのに
プレースホルダ検査は緑のままになる。`assertProse(source, survives)` で
**散文として残っていること**まで見る（coderabbit, #2993）。
