# #2842 の残り — replay ポリシーと fail-fast

#2898 で可観測性（提案1）と CLI バージョンの記録は入った。この plan は #2842 に残っている
**提案3（replay ポリシー）** と **提案2（fail-fast）** を扱う。報告者の追加指摘（ログの置き場所）は
別スコープなので含めない。

## 前提として直すもの（P）— ビーコンを「落ちない」ものにする

`reportBrokerReady`（`server/agent/mcp-server.ts`）は 2 秒タイムアウトの単発 POST で、
失敗すると `.catch(() => {})` に消えて二度と再送されない。

これまでビーコンは **warn の材料** でしかなかったので、落ちても「診断が 1 行減る」だけだった。
`shouldWarnMcpUnavailable` が `builtinMcpToolsCalled === 0` を条件に入れているのは、
まさに「ビーコンは落ちうる」ことを織り込んでいるから。

提案3 と提案2 はどちらもビーコンを **制御の入力** に昇格させる。落ちたビーコンが
「ブローカーが起動しなかった」と読まれると、健全なターンを誤って切る側に倒れる。
だから先に信頼性を上げる:

- タイムアウトを 2s → 5s（ハンドシェイクは既に返した後なので、待っても誰も損しない）
- 失敗したら 1 秒あけて最大 3 回まで再送。fire-and-forget は維持（`initialize` を絶対に遅らせない）
- 全部落ちたら stderr に 1 行残す

## 提案3 — ブローカーが来ていないなら replay しない

### 今の挙動

`handlePermission not found` → `recoverBrokerNotReady` が 3 秒待って 1 回だけ同じターンを再実行
（`budgets.broker = 1`）。ブローカーがそもそも起動していない場合、2 回目も 60 秒の connect wait を
座って待ってから同じエラーになる。報告者の実測で 100.8 秒。

### 変更

**待つ前ではなく、待った後に判断する。** これが重要で、判断を待つ前に置くと #2057 のレース回復を壊す:
ビーコンは `initialize` に応答した時点で飛ぶので、「レースに僅差で負けたブローカー」のビーコンは
エラーの直後にはまだ来ていない。3 秒待つのはもともとそのためだった。

| 待つ前 | 待った後 | 判定 | 何が起きていたか |
|---|---|---|---|
| ready | ready | replay する | ブローカーは応答していた。CLI 側のレース |
| 未 | ready | replay する | #2057。僅差で負けたが今は繋がっている |
| 未 | 未 | **replay しない** | #2842。来ていないので再実行しても同じ結果 |

- 判定そのものは `judgeBrokerReplay(readyBeforeWait, readyAfterWait)` として `retryPolicy.ts` に
  純粋関数で置く。3 つの理由（`ready-before-wait` / `ready-during-wait` / `never-ready`）を返し、
  ログにもその文字列をそのまま載せる。
- replay しないと決めたとき、**飲み込んだエラーイベントを出し直す**。今は `streamOnce` が
  recovery のトリガーになったイベントを握りつぶして `break` するので、そのまま抜けると
  ユーザーには何も出ない。`streamOnce` の戻り値に載せて、打ち切る側で `handleAgentEvent` に流す。
- `discardAbortedPass`（中断したパスの本文を捨てる）は **replay するときだけ** 呼ぶ。
  打ち切るときはそのパスが最終パスなので、今の 2 回目と同じように本文を残す。

効果: 100s → ~55s。1 回目の 60 秒天井は依然として座って待つ（そこは提案2 の担当）。

## 提案2 — 実測の結果、fail-fast は割に合わないと判断した

### 当初の設計

60 秒の天井は下げない（遅いが必ず来るブローカーを殺すと #2201 の flake が戻る）。
打ち切る条件は経過時間ではなく **liveness シグナルの不在** にする。ready ビーコンは
コールドブートの「後」に飛ぶので、待っている最中は使えない。だから
**start シグナル**（プロセス開始直後、import グラフの評価前）を足し、それが来なければ
「そもそも起動していない」と判定して CLI を打ち切る。

start シグナルは `--import` プリロードから出す。tsx 経路ではエントリのコードは
グラフ全体の変換後にしか走らないため、import ゼロの `.mjs` を `--import` で先に評価させる。

### 実測してわかったこと

**① 「起動しないブローカー」は CLI がすでに速く失敗させている。**
Docker モード（天井 60 秒）でブローカーのコマンドを実在しないバイナリに差し替えると、
CLI は **8.9 秒**でエラーを出した。しかもその間にモデルはテキストを流しツールを 2 回呼んでいる。
spawn 自体が即座に失敗するので、CLI は connect の天井を待たない。
watchdog をどの deadline に置いてもここには何も足せない。

**② 報告者の ~50 秒は「起動したブローカー」だった。**
tsx が変換している最中＝プロセスは生きている。start シグナルは `started=true` を返すので、
watchdog は設計どおり手を出さない。つまり #2842 の症状そのものには効かない。

**③ start マーカーは「起動した」ことしか証明しない。**
同期書き込みは狙いどおり早く、boot が 949ms のプロセスで **59ms** 時点に着地した
（非同期 fetch は event loop をブロックする変換の後ろに詰まり、ready ビーコンとの差は 2ms しかない）。
だが早すぎるがゆえに、ロード中にクラッシュしたブローカーもマーカーを書き終えている。

**結論**: watchdog が捕まえられる唯一のケースは既に速く、遅いケースは watchdog が触っては
いけないもの。ライブなターンを kill するリスクだけが残るので、**fail-fast は作らない**。

### 代わりに残すもの — 起動と応答を分ける診断

今の `brokerEverReady=false` は「一度も起動しなかった」と「起動したが boot が終わらなかった」を
区別できない。しかも `error-recovery.md` は前者だと**断定して**いた。実測はその推論が
成り立たないことを示している。

- start シグナルは 2 系統。ブロックする boot を追い越せる **同期マーカーファイル**（主）と、
  共有ファイルシステムを必要としない **HTTP ビーコン**（従）。どちらか来れば「起動した」。
  片方が塞がれても診断が落ちないため。
- マーカーは **spawn 単位**。replay で 2 本目が起動するとき、1 本目のマーカーが残っていても
  取り違えない。ターン終了時に MCP config と一緒に消す。
- `MCP tools were unavailable` の warn に `brokerEverStarted` を載せ、hint を 2 つに分ける。
- kill しないので、シグナルが落ちても失うのはログの 1 フィールドだけ。

## PR の分け方

1. **PR 1**: P（ビーコンの信頼性）+ 提案3（replay ポリシー）
2. **PR 2**: start シグナル（診断のみ。watchdog は上記の実測により作らない）

## 検証

- `yarn format` → `yarn lint` → `yarn typecheck` → `yarn build` → `yarn test`
- ユニットテスト:
  - `judgeBrokerReplay` の 3 ケース（+ 起こり得ない組み合わせの扱い）
  - ビーコン再送（1 回目失敗 → 2 回目成功、全滅、`initialize` を待たせない）
  - start ビーコン route（spawn 単位の受理・拒否、started ≠ ready）
  - マーカーのパス解決（Docker / native、spawn ごとに別、危険な id の無害化）
- Docker を有効にして実際に 1 ターン回し、正常系でこれらの変更が何も壊していないことを確認する。
  build が通ることは「動いた」の証拠にならない。
- 失敗系は人工的に起こす: ブローカーの spawn コマンドを壊して「起動しないブローカー」を作り、
  replay が消えることと、`brokerEverStarted` が正しく分かれることを実測する。
